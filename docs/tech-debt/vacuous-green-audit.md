## 왜 이 원장이 필요한가

D19(2026-09-14)에서 **한 건**을 고치고 끝냈다. 같은 결함이 **같은 파일 안에**,
그리고 다른 스펙에도 남아 있었다. 한 건씩 대응하면 계속 새로 발견된다 →
**한 번에 전수로 훑고 규칙으로 고정**한다.

결함의 형태는 하나다:

> **"무엇을 검증하려는가"(특정 영역의 값) 와 "무엇을 찾고 있는가"(페이지/화면 전체의 텍스트)가 어긋난다.**

`findByText` / `getByText` 는 **렌더 트리 전체**를 본다. 그래서
프리셋 칩·로딩 문구·이웃 라벨처럼 **항상 존재하는 텍스트**에 걸리면,
검증 대상이 망가져도 초록이 된다.

## 2. 약한 대기 (loading 상태를 settled 상태로 오인) — ✅ 교정 완료

> ⚠️ 이 진단은 **과소평가였다.** 실측 결과 "settle 이전에 시작될 수 있음"이 아니라
> **조회가 영원히 일어나지 않아도 통과**하는 상태였다(§5).

`findByText` 가 **로딩 중에도 참인 값**에 걸려 즉시 resolve → 그 뒤 단언이
**쿼리가 끝나기 전** 상태를 검사한다. 통과해도 의도한 계약을 보지 않는다.

| # | 위치 | 기다리는 값 | 문제 |
|---|---|---|---|
| **V2** | `__tests__/contexts/ProfileContext.test.jsx:90` | `findByText('0')` | 프로필 0건은 **로딩 중에도 0**. 이어지는 `selected === 'none'` 단언도 로딩 중 참 → **effect 가 아예 안 돌아도 통과** |
| **V3** | `__tests__/contexts/LifestyleGuideContext.test.jsx:85` | `findByText('0')` | 실패 전에도 count 0 → 참조 안정성 비교가 settle 이전에 시작될 수 있음 |
| **V4** | `__tests__/contexts/PrescriptionGroupContext.test.jsx:91` | `findByText('empty')` | 위와 동일 |

- **처방**: 대기 지점을 **상태가 실제로 바뀌는 값**에 건다
  (`waitFor(() => expect(getByTestId('error')).toHaveTextContent('true'))` 처럼
  settled 에서만 참인 값). 2026-09-14 의 1-d 작업에서 신규 4건은 이미 이 방식으로 작성했다.

## 4. 탐지 절차 — "결핍 주입(starvation injection)"

> A형(기능 없이도 통과)은 **"수정 전 Red"** 로 잡힌다.
> **B형(기능이 망가져도 통과)은 그걸로 안 잡힌다** — 수정 전엔 대상이 통째로 없으니
> 허술한 단언도 Red 가 되기 때문이다(대장 D21).
> B형을 잡는 건 아래 절차다.

**핵심 아이디어**: 코드를 망가뜨리는 대신 **데이터를 굶긴다.**
B형은 대부분 "테스트가 데이터가 아니라 **정적 UI** 를 보고 있다"에서 나오므로,
데이터를 없애거나 바꾸면 드러난다.

### 절차 (테스트 1건당 약 1분)

```
1. 그 테스트가 의존하는 스텁/시드를 찾는다
2. 값을 굶긴다 (아래 3단 레버 중 하나)
3. 재실행
4. Red 여야 정상. Green 이면 B형 확진
5. 원복
```

| 레버 | 방법 | 잡는 것 |
|---|---|---|
| **L1 비우기** | 스텁 배열 → `[]` | "목록이 렌더된다" 류의 허수 |
| **L2 바꿔치기** ⭐ | 스텁 값을 **고유 센티널**로 (`'E2E증상_QX7'`) | **정적 텍스트와의 충돌 — 가장 강력** |
| **L3 끊기** | 핸들러·콜백을 no-op 으로 | "클릭하면 저장된다" 류의 허수 |

**L2 는 탐지이자 예방이다.** 스텁 값이 화면 어디에도 없을 문자열이면,
선택자 스코프를 깜빡해도 결함이 **구조적으로 불가능**해진다.

> V1 은 이 절차(L1)로 **추측이 아니라 실행 결과**로 확진했다.

### 자동화 후보 — 뮤테이션 테스팅 (스파이크 필요)

결핍 주입을 *사람이 데이터에* 하는 것이라면, 뮤테이션 테스팅은 *기계가 코드에* 한다
(경계 변형·폴백 제거·분기 상수화 후 테스트가 죽이는지 측정).
**B형을 정면으로 겨냥하는 유일한 자동화 수단**이다.

- 도구: Stryker (Vitest 러너 지원, 2026 기준 활발히 유지)
- ⚠️ **우리 환경 미확인**: Vitest **5.0.0** / Node **22.14.0**(실측)에서 도는지 검증 안 됨
- 적용 층: **Vitest 층만**. E2E 뮤테이션은 느리고 비결정적이라 비현실적
- 게이트: 처음엔 **report-only** → baseline 확보 후 점수 게이트(6A MyPy 방식과 동일)
- 개념·근거 정본: `docs-private/study/vacuous-green-detection.md` §3

### 부수 발견 — 별건 부채 🟠

**`/medication` 진입 시 `prescription-groups` 가 반드시 두 번 조회된다.**

- **원인**: `PrescriptionGroupContext.jsx:116-124` — `medications` 가 도착하면
  `activeCount` 가 0→N 으로 바뀌며 `prescriptionGroups.all()` 을 invalidate 한다.
  첫 진입에서는 **항상** 발생하므로 중복 요청이 상시화돼 있다.
- **어떻게 드러났나**: 1-d 의 재시도 E2E 가 간헐 실패했다. 2차 조회가 주입 해제 뒤
  도착하면 **버튼을 누르지도 않았는데 화면이 복구**된다(전체 스위트 2회 중 1회 실패).
- **테스트 쪽 조치(완료)**: `e2e/helpers/query-failure.js` 가 주입 해제 전에
  "자동 재조회가 끝났는가"를 먼저 확인한다. 요청 **개수를 상수로 못 박지 않았다** —
  나중에 중복 조회가 제거되면 개수 단언은 영원히 대기하게 되기 때문.
- **잔여(behavior)**: 중복 조회 자체는 고치지 않았다. `fix`/`refactor` 단위로 분리해야
  하고 1-g-A 는 test-only 단위다. → **후속 큐로 이관**.
